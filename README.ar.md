# 🛒 متجر إلكتروني — Backend API

[English](README.md) | **العربية**

باك إند لمتجر إلكتروني مبني باستخدام **Express.js** و **MongoDB**، ويدعم:

- إدارة المنتجات مع إمكانية إضافة عدة صور للمنتج الواحد.
- سلة مشتريات بدون الحاجة لتسجيل الدخول باستخدام `Guest ID`.
- إنشاء وإدارة الطلبات.
- تأكيد الطلب عبر واتساب برمز يُستخدم مرة واحدة (التأكيد يدوي حالياً).
- متابعة الطلبات برمز التأكيد + رقم الهاتف (طلب واحد، أو عدة طلبات مرة واحدة).
- لوحة تحكم إدارية مع نظام صلاحيات متعدد المستويات، وإمكانية تفعيل وتعطيل حسابات الأدمن.
- حماية الـ API من إساءة الاستخدام والتحقق من المدخلات.
- معالجة تعارضات المخزون أثناء عمليات الشراء.
- اختبارات تكامل ووحدة باستخدام Jest و Supertest.

> 💡 هذا أول مشروع Backend حقيقي لي. بنيته بعد حوالي شهر ونصف من تعلم Express.js و MongoDB.

> هذا الملف يخص الـ Backend فقط. المستودع يحتوي على مجلدين: `backend/` و `frontend/`. راجع [ملف الـ Frontend](../frontend/README.ar.md).

| التقنية                  | الاستخدام                                  |
| ------------------------ | ------------------------------------------ |

| **Jest + Supertest**     | اختبارات الـ API                           |

## 📁 هيكل المشروع (Backend)

```text
backend/
├── myApp.js              # تعريف تطبيق Express (الـ middlewares والمسارات) — تستورده الاختبارات
├── server.js             # نقطة التشغيل: الاتصال بقاعدة البيانات، تشغيل السيرفر ومهمة الطلبات المنتهية
├── backups/              # نسخ احتياطية JSON من seedPhoneShop.js (غير موجودة في git)
├── scripts/              # سكربتات صيانة وترحيل بيانات وبيانات تجريبية (تُشغَّل يدوياً)
├── src/
│   ├── config/           # الاتصال بقاعدة البيانات
│   ├── controllers/      # منطق العمليات
│   ├── middlewares/      # المصادقة، الصلاحيات، التحقق، Rate Limiting، معالجة الأخطاء، فحص واتساب المتجر
│   ├── models/           # Admin, Cart, Item, Order, StoreSettings
│   ├── routes/           # تعريف المسارات
│   ├── services/         # orderConfirmation (رمز تأكيد واتساب)، stock (إرجاع / أخذ المخزون)، expireOrders (مهمة الطلبات المنتهية)
│   └── utils/            # ثوابت مشتركة (constants.js)، تنظيف رقم الهاتف (phone.js)
└── tests/
    ├── setup/            # الاتصال بقاعدة بيانات الاختبار
    ├── fixtures/         # بيانات جاهزة للاختبارات
    ├── helpers/          # دوال مساعدة (إنشاء أدمن تجريبي، إضافة منتج...)
    ├── integration/      # اختبارات الـ endpoints
    └── unit/             # اختبارات الوحدة
```

### ملفات المسارات

| الملف                | المسار الأساسي   | المحتوى                     |
| -------------------- | ---------------- | --------------------------- |
| `authRoutes.js`      | `/api/auth`      | تسجيل دخول الأدمن           |
| `adminRoutes.js`     | `/api/admins`    | إدارة حسابات الأدمن         |
| `dashboardRoutes.js` | `/api/dashboard` | الإحصائيات                  |
| `itemRoutes.js`      | `/api/items`     | المنتجات                    |
| `cartRoutes.js`      | `/api/carts`     | السلة                       |
| `orderRoutes.js`     | `/api/orders`    | الطلبات                     |

مسار إتمام شراء السلة (`POST /api/carts/:guestId/checkout`) موجود في `cartRoutes.js`، لكنه يستخدم `orderController`.

تم فصل `myApp.js` عن `server.js` حتى تتمكن الاختبارات من استيراد التطبيق وتشغيله بدون فتح منفذ أو الاتصال بقاعدة البيانات الرئيسية.

## ⚙️ الإعداد والتشغيل

جميع الأوامر التالية تُنفَّذ من داخل مجلد `backend/`.

### 1. تثبيت الحزم

```bash
cd backend
npm install
```

### 2. إعداد متغيرات البيئة

أنشئ ملف `.env` **داخل مجلد `backend/`**:

```env
PORT=5000
MONGO_URI=your_mongodb_connection_string
JWT_SECRET=your_jwt_secret_key
FRONTEND_URL=http://localhost:5173
```

| المتغير        | مطلوب | ملاحظات                                                      |
| -------------- | ----- | ------------------------------------------------------------ |
| `MONGO_URI`    | نعم   | رابط الاتصال بـ MongoDB                                      |
| `JWT_SECRET`   | نعم   | المفتاح السري لتوقيع توكنات الأدمن                           |
| `FRONTEND_URL` | نعم   | الـ origin الوحيد المسموح في CORS (عنوان الـ Frontend)        |
| `PORT`         | لا    | الافتراضي `5000`                                             |
| `MONGO_URI2`   | لا    | فقط لسكربت `scripts/seedPhoneShop.js` (القاعدة التي يملؤها بمنتجات تجريبية). السيرفر لا يستخدمه |
| `WHATSAPP_BOT_ENABLED` | لا | القيمة `true` تضيف مسار البوت `GET /api/orders/:id/confirmation`. اتركه فارغاً حالياً |

عند تشغيل السيرفر (`server.js`) يتم التحقق من `MONGO_URI` و`JWT_SECRET` و`FRONTEND_URL`. إذا كان أحدها مفقوداً، يطبع `Missing environment variables: ...` ويتوقف.

### 3. تشغيل السيرفر

```bash
npm start
```

أو للتطوير مع إعادة التشغيل التلقائية عند تعديل الملفات (nodemon):

```bash
npm run dev
```

يبدأ السيرفر بالاتصال بقاعدة البيانات، وإذا فشل الاتصال يتوقف التشغيل مباشرة. بعد نجاحه يعمل افتراضياً على:

```text
http://localhost:5000
```

### 4. التأكد من أن السيرفر يعمل

```http
GET /health
```

الاستجابة:

```json
{
  "status": "ok"
}
```

> ملاحظة: الـ `/health` endpoint محمي أيضاً باستخدام Rate Limiting، وهو خارج المسار `/api`.

# 🧪 الاختبارات

```bash
npm test
```

يتم تشغيل الاختبارات عبر `jest --runInBand` (ملف بعد ملف). التشغيل المتوازي (`npx jest`) يعمل أيضاً، لأن كل ملف له قاعدة بيانات خاصة.

### قاعدة بيانات الاختبار (في الذاكرة)

الاختبارات تستخدم **[mongodb-memory-server](https://github.com/typegoose/mongodb-memory-server)**: قاعدة MongoDB حقيقية تعمل **في الذاكرة** على جهازك. بدون Atlas، وبدون إنترنت، وبدون قائمة IP.

- كل ملف اختبار يشغّل قاعدة فارغة خاصة به (`testingDataBase`) ويحذفها عندما ينتهي (`tests/setup/db.js`).
- الاختبارات لا يمكن أن تلمس قاعدة حقيقية: تتوقف إذا لم يكن العنوان `127.0.0.1`.
- **أول تشغيل** يحمّل ملف MongoDB مرة واحدة (حوالي 1–2 دقيقة). بعدها يُحفظ، وكل الاختبارات تأخذ ثوانٍ قليلة.
- ملف `.env.testing` **اختياري**. يعطي `JWT_SECRET` فقط (`MONGO_URI` لا يُستخدم). بدونه تستخدم الاختبارات `"test-secret"`.

> MongoDB driver 7 يحمّل `os` باستخدام `import()` ديناميكي، و Jest يمنع ذلك، فيرفض السيرفر الاتصال ("Missing required sub-document 'driver'"). ملف `db.js` يحل المشكلة بإعطاء الـ driver الـ `os` مباشرة: `mongoose.connect(uri, { runtimeAdapters: { os } })`.

### ما الذي تغطيه الاختبارات؟

| الملف                     | ماذا يختبر                                                                                                      |
| ------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `items.test.js`           | جلب المنتجات، الإضافة والتعديل بواسطة أدمن، رفض التوكن المفقود أو غير الصالح، رفض الأدمن المعطّل، رفض البيانات غير الصالحة (سعر سالب، روابط `javascript:`)، والمعرّفات غير الصالحة أو غير الموجودة |
| `orders.test.js`          | الشراء المباشر: النجاح يحدّث المخزون والإجمالي؛ رفض المعرّف غير الصالح، الكمية غير الصالحة، الكمية الأكبر من المخزون، والمنتج غير الموجود. **تعارض المخزون:** طلبان متزامنان على مخزون يكفي لطلب واحد ← واحد `201` وواحد `400`، ويُحفظ طلب `1` فقط. **تأكيد واتساب:** الشراء يرجع رمزاً ورابط `wa.me`؛ `503` بدون رقم المتجر؛ `GET /:id/confirmation` يرجع `404` والبوت متوقف؛ المشرف يؤكد مرة واحدة فقط (`409` في المرة الثانية)؛ رقم خاطئ ← `PHONE_MISMATCH`؛ صلاحية `admin` ← `403`. **التتبّع:** `/track` ينظّف الرمز والرقم، ويرفض الكائنات (injection) والرقم الخاطئ؛ `/track-many` يرجع `found` / `notFound` / `invalid` بالترتيب، ولا يعرض طلبات أخرى لنفس الرقم، ويرفض القائمة الفارغة أو الطويلة (أكثر من 20)؛ والمسار القديم `/api/guest/sessions` يرجع `404`. **الإلغاء:** `/cancel` يلغي طلب `Pending` مرة واحدة ويرجع المخزون (الضغطة الثانية ← `409`، والمخزون لا يرجع مرتين)؛ يرفض الرقم الخاطئ (`404`) والـ injection (`400`) والطلب `Accepted` (`409`)؛ الطلب الملغي لا يمكن تأكيده (`CANCELLED`). **حالة الأدمن:** إلغاء الأدمن يرجع المخزون مرة واحدة (`cancelledBy: "admin"`)؛ إعادة فتح الطلب تأخذ المخزون مرة أخرى، أو تُرفض بـ `NOT_ENOUGH_STOCK`؛ تغيير الحالات الأخرى لا يحرّك المخزون؛ الزبون لا يستطيع إلغاء طلب ألغاه الأدمن. **المنتهية:** الطلب `Pending` المنتهي يصبح `Cancelled` (`cancelledBy: "system"`) ومخزونه يرجع مرة واحدة فقط؛ الطلبات الجديدة والمؤكدة والمقبولة لا تتأثر؛ الطلب الذي ألغاه الزبون لا يرجع مخزونه مرتين |
| `auth.test.js`            | مسارات الأدمن ترجع `401` بدون توكن، أو بتوكن مزيّف، أو بتوكن صحيح لأدمن غير موجود                              |
| `health.test.js`          | `GET /health` يرجع `200`                                                                                        |
| `cart.test.js`            | إضافة نفس المنتج مرتين تجمع الكمية في **سطر واحد** في السلة (2 + 3 = 5)، والإضافة للسلة لا تُنقص المخزون |

جميع الاختبارات (**46**) تنجح.

# 🔑 نظام الصلاحيات (Roles)

يحتوي النظام على **3 مستويات من الصلاحيات**، ويتم حماية كل endpoint إداري حسب الصلاحية المطلوبة.

| الرتبة        | الصلاحيات                                                                              |
| ------------- | -------------------------------------------------------------------------------------- |
| `admin`       | إضافة، تعديل وحذف المنتجات                                                             |
| `moderator`   | جميع صلاحيات `admin` بالإضافة إلى إدارة الطلبات                                        |
| `super_admin` | جميع الصلاحيات بالإضافة إلى إدارة حسابات الأدمن (إنشاء، تفعيل، تعطيل) والوصول للإحصائيات |

### مصادقة الأدمن

تتم المصادقة باستخدام **JWT Bearer Token**:

```http
Authorization: Bearer <token>
```

- التوكن صالح لمدة **48 ساعة**، ويحتوي على `id` و`role` الخاصين بالأدمن.
- الحساب المعطّل لا يستطيع تسجيل الدخول (`403`).
- الحساب المعطّل (`isActive: false`) يتم رفض طلباته أيضاً بـ `401` حتى لو كان التوكن الخاص به لا يزال صالحاً.
- كل طلب ناجح للأدمن يحدّث `lastActivityAt` الخاص به.
- بدون توكن أو بصلاحية غير مناسبة ← `401` / `403`.

# 🗄️ نماذج البيانات (Models)

## 🛍️ المنتج (Item)

يمكن لكل منتج أن يحتوي على عدد ديناميكي من الصور، حيث يتم تخزين الصور كمصفوفة من الكائنات بدلاً من الاعتماد على رابط صورة واحد.

| الحقل          | النوع            | الملاحظات                                                         |
| -------------- | ---------------- | ----------------------------------------------------------------- |
| `images`       | `[{ imageURL }]` | مصفوفة صور، افتراضياً فارغة، وكل صورة يجب أن تحتوي على `imageURL` |
| `itemName`     | `String`         | مطلوب                                                             |
| `itemPrice`    | `Number`         | مطلوب، ولا يمكن أن يكون أقل من `0`                                |
| `itemQuantity` | `Number`         | الافتراضي `0`، ولا يمكن أن يكون أقل من `0`                        |

### مثال

```json
{
  "images": [
    {
      "imageURL": "https://example.com/img1.jpg"
    },
    {
      "imageURL": "https://example.com/img2.jpg"
    }
  ],
  "itemName": "اسم المنتج",
  "itemPrice": 50,
  "itemQuantity": 10
}
```

## 👤 الأدمن (Admin)

| الحقل            | النوع     | الملاحظات                                                          |
| ---------------- | --------- | ------------------------------------------------------------------ |
| `fullName`       | `String`  | مطلوب                                                              |
| `firstName`      | `String`  | يُحسب تلقائياً من أول كلمة في `fullName` عند الحفظ                 |
| `email`          | `String`  | مطلوب، فريد، يُحفظ بأحرف صغيرة                                     |
| `password`       | `String`  | مطلوب، مشفّر، ولا يُرجَع في الاستعلامات افتراضياً (`select: false`) |
| `role`           | `String`  | `admin` / `moderator` / `super_admin`، والافتراضي `admin`          |
| `isActive`       | `Boolean` | الافتراضي `true`، والحساب المعطّل لا يستطيع تنفيذ العمليات         |
| `lastActivityAt` | `Date`    | آخر نشاط للحساب، الافتراضي `null`                                   |

## 📦 الطلب (Order)

| الحقل          | النوع    | الملاحظات                                                                  |
| -------------- | -------- | -------------------------------------------------------------------------- |
| `customerName` | `String` | مطلوب                                                                      |
| `phoneNumber`  | `String` | مطلوب. يُحفظ كرمز الدولة + الرقم، مثل `+970599123456`                       |
| `region`       | `String` | مطلوب. قيمة من قائمة `REGIONS` في `src/utils/constants.js`                  |
| `items`        | `Array`  | كل عنصر يحتوي على `itemId` و`itemName` و`itemPrice` و`quantity`           |
| `totalPrice`   | `Number` | مطلوب                                                                      |
| `status`       | `String` | `Pending` (الافتراضي) / `Accepted` / `Delivered` / `Cancelled`             |
| `confirmation` | `Object` | تأكيد واتساب (انظر بالأسفل). الطلبات القديمة لا تحتوي عليه                 |
| `cancelledAt`  | `Date`   | وقت إلغاء الطلب (اختياري)                                                  |
| `cancelledBy`  | `String` | `customer` أو `admin` أو `system` (انتهى التأكيد): من ألغى الطلب (اختياري) |

حقول `confirmation`:

| الحقل         | النوع    | ملاحظات                                                                    |
| ------------- | -------- | -------------------------------------------------------------------------- |
| `code`        | `String` | 6 خانات من `A–Z` و`2–9` بدون `0 O 1 I L` (سهلة القراءة). فريد              |
| `status`      | `String` | `pending` (الافتراضي) / `confirmed` / `expired`                            |
| `expiresAt`   | `Date`   | بعد **24 ساعة** من الطلب (`CONFIRM_TTL_MINUTES` في الـ service)            |
| `confirmedAt` | `Date`   | وقت التأكيد                                                                |
| `method`      | `String` | من أكّد: `whatsapp_bot` أو `manual` في قائمة الـ schema. مسار الأدمن يحفظ `admin` |

الـ Indexes: (`phoneNumber`, `createdAt`) لتسريع جلب طلبات المستخدم، و`confirmation.code` (فريد)، و(`confirmation.status`, `confirmation.expiresAt`).

## ⚙️ إعدادات المتجر (StoreSettings)

مستند واحد للمتجر كله (`key: "main"`).

| الحقل            | النوع      | ملاحظات                                                              |
| ---------------- | ---------- | -------------------------------------------------------------------- |
| `key`            | `String`   | دائماً `"main"`. فريد ولا يمكن تغييره                                |
| `whatsappNumber` | `String`   | رقم واتساب المتجر. يُنظَّف بـ `normalizePhone`، مثل `+970599123456`   |

> ⚠️ إذا لم يوجد `whatsappNumber`، **يتم منع كل عمليات الشراء** بـ `503` ("الشراء غير متاح حالياً"). احفظه باستخدام [`storeSettingsSeed.js`](#-رقم-واتساب-المتجر-storesettingsseedjs).

# 📚 توثيق الـ API Endpoints

جميع المسارات تحت `/api`، وجميع الاستجابات من هذا المسار تحمل `Cache-Control: no-store`.

## 🛍️ المنتجات (Items)

| Method   | Endpoint              | الصلاحية | الوصف             |
| -------- | --------------------- | -------- | ----------------- |
| `GET`    | `/api/items`          | عام      | جلب جميع المنتجات |
| `POST`   | `/api/items`          | `admin+` | إضافة منتج جديد   |
| `PUT`    | `/api/items/:id`      | `admin+` | تعديل منتج        |
| `DELETE` | `/api/items/:id`      | `admin+` | حذف منتج          |

> `admin+` تعني: `admin` أو `moderator` أو `super_admin`. وبنفس الطريقة `moderator+` تعني: `moderator` أو `super_admin`.

### قواعد الإضافة والتعديل (`POST` و`PUT`)

| الحقل          | القاعدة                                                     |
| -------------- | ----------------------------------------------------------- |
| `itemName`     | مطلوب، بحد أقصى **100** حرف                                 |
| `itemPrice`    | رقم من `0` إلى **1,000,000**                                |
| `itemQuantity` | عدد صحيح من `0` إلى **100,000**                             |
| `images`       | من **1 إلى 6** صور؛ كل `imageURL` يجب أن يكون `http`/`https` وبحد أقصى **500** حرف |

الحدود موجودة في `ITEM_LIMITS` داخل `src/utils/constants.js`.

### بيانات الشراء (Body)

الشراء المباشر (`POST /api/orders`):

```json
{

  "quantity": 2,
  "purchaseDetails": {
    "fullName": "اسم العميل",
    "countryCode": "+970",
```

- `region`: إحدى القيم في `REGIONS` (`src/utils/constants.js`)، مثل `hebron` و`dura` و`yatta`.

# 💬 تأكيد الطلب عبر واتساب

كل طلب جديد يجب أن يؤكده الزبون على واتساب. هذا يثبت أن الزبون يملك رقم الهاتف فعلاً.

1. الزبون يشتري (مباشر أو من السلة). يُحفظ الطلب مع `confirmation.status: "pending"` ورمز من 6 خانات.
2. مسارا الشراء يرجعان:

```json
{
  "data": {
    "orderId": "...",
    "confirmCode": "K7P2XM",
    "expiresAt": "2026-11-23T15:35:00.000Z",
    "whatsappUrl": "https://wa.me/970599123456?text=..."
  }
}
```

3. `whatsappUrl` يفتح محادثة مع رقم المتجر، والرسالة مكتوبة جاهزة:

```text
تأكيد طلب
رمز التأكيد: K7P2XM
```

4. المشرف يؤكد الطلب يدوياً بعد رؤية الرسالة (`POST /api/orders/confirm`).
5. الزبون يستطيع رؤية الطلب وحالة تأكيده بالرمز (`POST /api/orders/track`، انظر بالأسفل) أو من صفحة "طلباتي".

> 🚧 المسار `GET /api/orders/:id/confirmation` لبوت واتساب المستقبلي. يُضاف **فقط** عندما `WHATSAPP_BOT_ENABLED=true`، ويحتاج صلاحية `bot`. يرجع `pending` أو `confirmed` أو `expired` (الطلب `pending` بعد `expiresAt` يظهر `expired`؛ الطلبات القديمة بدون `confirmation` ترجع `confirmed`). الـ Frontend لا يستخدمه.

### تتبّع الطلب (`POST /api/orders/track`)

```json
{ "code": "K7P2XM", "phoneNumber": "+970599123456" }
```

الزبون يحتاج **الاثنين معاً**: الرمز ورقم الهاتف. الـ middleware `validateTrackOrder.js` يفحصهما قبل قاعدة البيانات:

- الاثنان يجب أن يكونا نصاً. الكائنات مثل `{ "$ne": null }` تُرفض (NoSQL injection).
- `code`: تُحذف المسافات وتصبح الحروف كبيرة (`k7p 2xm` ← `K7P2XM`). بعدها يجب أن يكون 6 خانات من حروف رمز التأكيد (بدون `0 O 1 I L`).
- `phoneNumber`: يُنظَّف بـ `normalizePhone`، مثل صفحة الشراء (`+970 0599-123-456` ← `+970599123456`).
- القيم النظيفة تصل للـ controller في `res.locals.tracking`.
- حد الطلبات: **20**.

| الحالة                                        | الكود |
| --------------------------------------------- | ----- |
| تم العثور عليه (`data` هو الطلب كاملاً)        | `200` |
| الرمز أو الرقم مفقود أو ليس نصاً              | `400` |
| شكل الرمز غير صحيح                            | `400` |
| رقم الهاتف غير صحيح                           | `400` |
| لا يوجد طلب بهذا الرمز **وهذا** الرقم          | `404` |

> الرقم يجب أن يطابق تماماً: الطلب المحفوظ بـ `+970` لا يُوجد بـ `+972` (التأكيد اليدوي يعتبرهما نفس الرقم، التتبّع لا).

### تتبّع عدة طلبات (`POST /api/orders/track-many`)

تستخدمه صفحة "طلباتي": المتصفح يحفظ `{ code, phoneNumber }` لكل طلب، ويطلب بيانات جديدة لها كلها في طلب **واحد** (استعلام واحد لقاعدة البيانات).

```json
{
  "orders": [
    { "code": "K7P2XM", "phoneNumber": "+970599123456" },
    { "code": "ABCDEF", "phoneNumber": "+970599123456" },
    { "code": "bad", "phoneNumber": "+970599123456" }
  ]
}
```

الرد (بنفس الترتيب والطول):

```json
{
  "success": true,
  "data": [
    { "code": "K7P2XM", "phoneNumber": "+970599123456", "status": "found", "order": { "...": "..." } },
    { "code": "ABCDEF", "phoneNumber": "+970599123456", "status": "notFound" },
    { "code": "bad", "phoneNumber": "+970599123456", "status": "invalid" }
  ]
}
```

- `orders` يجب أن تكون مصفوفة فيها **من 1 إلى 20** عنصر، وإلا يُرفض الطلب كله بـ `400`.
- كل عنصر يُفحص بنفس قواعد `/track` (`validateTrackMany` في `validateTrackOrder.js`).
- العنصر الخاطئ **لا** يرفض الطلب. يرجع `"invalid"`، حتى لا يخفي طلبٌ محفوظ تالف باقي الطلبات.
- `code` و`phoneNumber` في الرد هما ما أرسله المتصفح، ليطابق كل رد مع طلبه المحفوظ.
- لا يعرض أبداً طلبات أخرى لنفس الرقم: فقط الطلبات التي ترسل رمزها.
- حد الطلبات: **60**.

### إلغاء الزبون للطلب (`POST /api/orders/cancel`)

يستخدمه زر **إلغاء الطلب** في صفحة "طلباتي".

```json
{ "code": "K7P2XM", "phoneNumber": "+970599123456" }
```

- الرمز والرقم يُفحصان بنفس قواعد `/track` (`validateTrackOrder`).
- يمكن إلغاء الطلب **`Pending`** فقط (المتجر لم يقبله بعد).
- الطلب يصبح `Cancelled`، مع `cancelledAt` و`cancelledBy: "customer"`.
- **المخزون يرجع**: كل منتج يأخذ كميته مرة أخرى. المنتج المحذوف يُتجاوز.
- تحديث واحد atomic (`findOneAndUpdate` مع `status: "Pending"`). لذلك ضغطتان بنفس اللحظة ترجعان المخزون مرة واحدة فقط.
- الطلب الملغي لا يمكن تأكيده بعد ذلك (`CANCELLED` في جدول التأكيد اليدوي).
- حد الطلبات: **20**.

| الحالة                              | الكود | `code` في الرد       |
| ----------------------------------- | ----- | -------------------- |
| تم الإلغاء (الرد فيه الطلب)         | `200` | —                    |
| رمز أو رقم غير صحيح                 | `400` | —                    |
| لا يوجد طلب بهذا الرمز + الرقم      | `404` | —                    |
| مقبول، أو تم توصيله، أو ملغي مسبقاً | `409` | `NOT_CANCELLABLE`    |

> **تغيير الأدمن لحالة الطلب** (`PATCH /api/orders/:orderId`) يحرّك المخزون أيضاً:
> - إلى `Cancelled`: المخزون يرجع، والطلب يحفظ `cancelledBy: "admin"`.
> - من `Cancelled` (إعادة فتح الطلب): المخزون يُؤخذ مرة أخرى، ويُحذف `cancelledAt` / `cancelledBy`. إذا منتج واحد مخزونه غير كافٍ (أو محذوف)، لا يتغير شيء والرد `400` `NOT_ENOUGH_STOCK`.
> - بين الحالات الأخرى (`Pending` / `Accepted` / `Delivered`): المخزون لا يتغير.
> - التحديث يعمل فقط إذا لم تتغير الحالة في نفس الوقت، لذلك ضغطتان تحرّكان المخزون مرة واحدة فقط. غير ذلك: `409` `STATUS_CHANGED`.

### ⏳ الطلبات المنتهية (المخزون يرجع)

الطلب الذي **لم يُؤكَّد على واتساب خلال 24 ساعة** يلغيه السيرفر (`src/services/expireOrders.service.js`):

- `server.js` يشغّل المهمة بعد الاتصال بقاعدة البيانات. تعمل **مرة عند التشغيل** (لتلحق ما فات إذا كان السيرفر نائماً)، ثم **كل 10 دقائق**. الاختبارات لا تشغّلها.
- تبحث عن الطلبات التي فيها `status: "Pending"` و`confirmation.status: "pending"` و`confirmation.expiresAt` في الماضي (الـ index على `confirmation.status` + `confirmation.expiresAt` يجعل البحث سريعاً).
- كل طلب يصبح `status: "Cancelled"` و`confirmation.status: "expired"` و`cancelledBy: "system"`، و**مخزونه يرجع** (`returnStock` في `src/services/stock.service.js`).
- تحديث atomic واحد لكل طلب، لذلك المخزون يرجع مرة واحدة فقط (حتى لو ألغى الزبون في نفس اللحظة).
- **لا تتأثر:** الطلبات المؤكدة، والطلبات التي قبلها الأدمن.
- الأدمن يستطيع إعادة فتح طلب منتهي: المخزون يُؤخذ مرة أخرى، أو يُرفض التغيير بـ `NOT_ENOUGH_STOCK`.

### التأكيد اليدوي (`POST /api/orders/confirm`)

```json
{ "code": "K7P2XM", "senderPhone": "+970599123456" }
```

- `senderPhone` يجب أن يكون رقم الطلب. `+970` و`+972` يُعتبران نفس الرقم (`isSamePhone` في `src/utils/phone.js`).
- التحديث يعمل فقط إذا كان الطلب ما زال `pending` ولم تنتهِ صلاحيته. لذلك إذا أكّد شخصان بنفس اللحظة، ينجح واحد فقط.
- نفس الدالة (`confirmOrderByCode` في `src/services/orderConfirmation.service.js`) جاهزة لبوت واتساب لاحقاً.

| الحالة                         | الكود | `code` في الرد       |
| ------------------------------ | ----- | -------------------- |
| تم التأكيد                     | `200` | —                    |
| شكل الرمز غير صحيح             | `400` | `INVALID_CODE`       |
| الرقم ليس رقم الطلب            | `400` | `PHONE_MISMATCH`     |
| لا يوجد طلب بهذا الرمز         | `404` | `NOT_FOUND`          |
| مؤكد مسبقاً                    | `409` | `ALREADY_CONFIRMED`  |
| الزبون ألغى الطلب              | `409` | `CANCELLED`          |
| مرّ أكثر من 24 ساعة            | `410` | `EXPIRED`            |

# 🛡️ الحماية والأمان

يحتوي المشروع على مجموعة من الإجراءات الأمنية والحمايات:

### 🚦 Rate Limiting

كل endpoint محمي بحد أقصى لعدد الطلبات خلال فترة **15 دقيقة** (لكل IP)، مع اختلاف الحد حسب حساسية الـ endpoint (مثلاً: 5 طلبات لإنشاء أدمن جديد، و10 لتسجيل الدخول وتفعيل/تعطيل الأدمن، و20 لتتبّع طلب واحد، و60 لتتبّع عدة طلبات، و20 للإلغاء). عند تجاوز الحد ← `429`.

الهدف هو تقليل احتمالية إساءة استخدام الـ API.

### 🌍 CORS

إعداد CORS يسمح بـ origin واحد فقط: قيمة `FRONTEND_URL`.

### ✅ Validation

يتم التحقق من المدخلات قبل معالجتها، بما في ذلك:

- الأسعار.
- الكميات.
- روابط الصور (مع رفض الروابط الخطرة مثل `javascript:`).
- أرقام الهواتف.
- `guestId`.
- معرّفات MongoDB `ObjectId`.
- وغيرها من المدخلات.

### ⚠️ معالجة الأخطاء المركزية (Centralized Error Handler)

يوجد Middleware مركزي لمعالجة الأخطاء (`errorMiddleware.js`) يحوّل الأخطاء الشائعة إلى استجابات مفهومة:

| نوع الخطأ                              | الكود |
| -------------------------------------- | ----- |
| `ValidationError` (أخطاء Mongoose)     | `400` |
| `CastError` (معرّف غير صالح)           | `400` |
| `TokenExpiredError` / `JsonWebTokenError` | `401` |
| قيمة مكررة (`E11000`)                  | `409` |
| أي خطأ غير متوقع                       | `500` |

### 📨 شكل واحد لرسائل الخطأ

كل رد خطأ (الـ controllers، الـ middlewares، الـ rate limit، الـ 404، معالج الأخطاء) له نفس الشكل:

```json
{
  "success": false,
  "message": "السلة غير موجودة!",
  "code": "NOT_CANCELLABLE"
}
```

- `message` نص عربي قصير. الـ Frontend يعرضه للمستخدم في toast، لذلك يجب أن يكون آمناً وواضحاً للزبون.
- `code` اختياري. موجود عندما يحتاج الـ Frontend أو الاختبار معرفة الحالة بالضبط (مثلاً `NOT_CANCELLABLE`، `NOT_ENOUGH_STOCK`، `ALREADY_CONFIRMED`).
- لا يوجد مفتاح `error`. ردود السلة القديمة كانت تستخدم `error`، فكان الـ Frontend يعرض رسالة عامة بدلاً منها. الآن تستخدم `message` أيضاً.

### 🚧 404 للمسارات غير الموجودة

إذا لم يتطابق أي مسار، يوجد middleware في `myApp.js` (بعد جميع المسارات وقبل `errorHandler`) يرجع JSON:

```json
{
  "success": false,
  "message": "Route not found"
}
```

### 📦 معالجة تعارض المخزون (Stock Race Conditions)

عمليات الشراء تستخدم تحديثات ذرية عبر:

```text
findOneAndUpdate
```

مع شرط التحقق من توفر الكمية.

هذا يمنع بيع كمية أكبر من المخزون المتوفر في حال وجود عدة عمليات شراء في نفس الوقت، وهذا السلوك مغطّى باختبار تكامل يرسل طلبين متزامنين.

كما توجد آلية **Rollback** تلقائية في حال فشل أي جزء من عملية شراء تحتوي على عدة منتجات.

### 🔐 تشفير كلمات المرور

يتم استخدام **bcrypt** لتشفير كلمات مرور الأدمن، ولا يتم تخزين كلمات المرور كنص صريح، كما أنها لا تُرجَع في الاستعلامات افتراضياً.

### 🔎 تتبّع الطلبات

لا توجد جلسات ضيف ولا توكنات. الزبون يرى الطلب فقط بـ **رمز التأكيد + رقم الهاتف**. لا يوجد endpoint يعرض كل طلبات رقم هاتف، لذلك معرفة رقم شخص ما لا تكفي. الرمز عشوائي (`crypto.randomInt`، حوالي 887 مليون احتمال) والتتبّع محدود بعدد الطلبات.

### 🚫 منع التخزين المؤقت

جميع المسارات تحت `/api` تُرجع:

```http
Cache-Control: no-store
```

لتقليل احتمالية تخزين بيانات الطلبات أو غيرها في الـ cache.

### 📏 حد حجم الطلب

تم تحديد حجم الـ request body إلى:

```text
1mb
```

لمنع إرسال بيانات ضخمة إلى السيرفر.

### 🌐 Trust Proxy

تم تفعيل:

```javascript
app.set("trust proxy", 1);
```

حتى يتمكن Rate Limiter من قراءة عنوان الـ IP الحقيقي للمستخدم عند تشغيل التطبيق خلف Proxy مثل **Render**.

# 📋 تسجيل الطلبات (Request Logging)

يتم تسجيل كل request في الـ console عند انتهاء معالجته. التسجيل **معطّل أثناء الاختبارات** (`NODE_ENV=test`).

المعلومات المسجلة تشمل:

- الوقت (وقت بداية الطلب).
- HTTP Method.
- URL.
- IP Address.
- HTTP Status Code.
- مدة معالجة الطلب.
- User-Agent.
- Referer.
- حجم الاستجابة.

ويتم تصنيف الطلبات حسب حالة الاستجابة:

| الحالة      | التصنيف           | المستوى         |
| ----------- | ----------------- | --------------- |
| `2xx / 3xx` | ✅ `REQUEST`      | `console.log`   |
| `4xx`       | ⚠️ `CLIENT ERROR` | `console.warn`  |
| `5xx`       | 🔥 `SERVER ERROR` | `console.error` |

### 📱 بيانات تجريبية: `seedPhoneShop.js`

يملأ قاعدة البيانات في **`MONGO_URI2`** (وليس `MONGO_URI`) بـ **22 منتجاً تجريبياً** لمتجر "Talahmeh Phones": هواتف، سماعات، شواحن، ساعات، وتابلت. المنتجات ليست حقيقية. بعض الكميات مقصودة لإظهار شارات المخزون (`0` = نفذت الكمية، `2`–`4` = كمية قليلة). شغّله من مجلد `backend/`:

```bash
node scripts/seedPhoneShop.js --dry-run            # عرض فقط، بدون أي تغيير
node scripts/seedPhoneShop.js                      # إضافة المنتجات غير الموجودة فقط (حسب الاسم)
node scripts/seedPhoneShop.js --dry-run --replace  # عرض ما سيفعله --replace
node scripts/seedPhoneShop.js --replace            # نسخة احتياطية ← حذف كل المنتجات ← إضافة الـ 22 منتجاً
```

- `--replace` يحذف **مجموعة `items` فقط**. الطلبات، السلات، والأدمن لا تتأثر.
- قبل الحذف يحفظ كل المنتجات الحالية في `backend/backups/items-<db>-<date>.json` ويتأكد من الملف. مجلد `backups/` موجود في `.gitignore`.
- الطلبات القديمة تحتفظ باسم المنتج وسعره بداخلها، لذلك تبقى تظهر بشكل صحيح. السلات القديمة قد تشير لمنتجات محذوفة حتى تنتهي صلاحيتها (7 أيام).
- قبل الكتابة يتحقق من نفس حدود الـ API (طول الاسم، السعر، الكمية، 1–6 صور).

### 💬 رقم واتساب المتجر: `storeSettingsSeed.js`

يحفظ رقم واتساب المتجر في `StoreSettings` (قاعدة البيانات في `MONGO_URI`). **الشراء لا يعمل حتى تشغّله مرة واحدة.** شغّله من `backend/`:

```bash
node scripts/storeSettingsSeed.js +970599123456
```

شغّله مرة أخرى برقم آخر لتغييره. الرقم الخاطئ يُرفض.

### ترحيل الصور من `imageURL` إلى `images`

كان المنتج يخزّن صورة واحدة في الحقل `imageURL`، ثم تم الانتقال إلى مصفوفة `images`. ترتيب التنظيف الآمن:

1. `checkLegacyImageURL.js` لمعرفة حالة المنتجات.
2. `checkBeforeCleanup.js` للتأكد أن كل منتج لديه `images`.
3. `cleanDatabase.js` لحذف `imageURL` القديم، وهذا الأمر **لا يملك وضع DRY RUN ولا يمكن التراجع عنه**، فخذ نسخة احتياطية قبله.

# 🩺 حل المشاكل الشائعة

### `querySrv ECONNREFUSED`

يظهر هذا الخطأ عند الاتصال برابط `mongodb+srv://` عندما لا يستطيع الـ DNS المحلي تحليل سجلات SRV. الحلول:

- تغيير DNS الجهاز إلى `8.8.8.8` أو `1.1.1.1`.
- استخدام رابط الاتصال القديم (غير SRV) من MongoDB Atlas.
- أو إضافة هذا السطر في بداية ملف التشغيل:

```javascript
require("dns").setServers(["8.8.8.8", "1.1.1.1"]);
```

> هذا السطر غير مضاف في كود السيرفر. والاختبارات لم تعد تحتاجه (تستخدم قاعدة في الذاكرة).

### `MongooseServerSelectionError` (الـ IP غير مسموح)

MongoDB Atlas يمنع أي IP غير موجود في القائمة. أضف الـ IP الخاص بك من Atlas ← **Network Access**.
